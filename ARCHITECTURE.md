# Architecture

For whoever works on this next. It covers the one decision everything else
follows from, the services involved and where to get at them, and the things
that cost a day to find out.

## Why no painting data is in this repository

The old site kept images in `static/` and their details in
`data/paintings.json`, both in git. Adding a painting meant committing a
binary and redeploying, so only a developer could do it.

Now the repo holds no painting data at all. That buys four things the family
actually asked for:

- edits are made in a browser, by them, not by a developer;
- a new version of the site cannot overwrite their work, because it ships none;
- the images are served and resized by a CDN instead of by the app;
- everything is exportable to a file they keep (`npm run metadata:export`).

The cost is that the site cannot be a pile of static HTML — it has to ask
ImageKit what exists. That is the trade behind the caching section below.

### Plan limits worth watching

ImageKit's free plan gives **20 GB bandwidth a month, as a hard limit** —
delivery stops when it is reached — and 3 GB of storage. The originals are
571 MB, so storage is not a concern. Bandwidth is fine because visitors are
served transformed WebP a few tens of KB in size rather than 2 MB originals,
but a link that goes around a large family could move the needle. Lite is
$9/month. Check usage at [Analytics](https://imagekit.io/dashboard/analytics).

## The painting schema

`lib/schema.ts` is the only definition. The read layer, the admin UI and the
scripts all import it, so they cannot drift.

`description` and `tags` are ImageKit's **native** file fields, deliberately —
that keeps them editable and searchable in the ImageKit dashboard. Everything
else is custom metadata.

> **Custom metadata field names are permanent.** ImageKit will not let you
> create a field with a name that has ever been deleted. Renaming means a new
> name and migrating the values. Labels and select options can change freely;
> `npm run schema:setup` widens select options to match `lib/schema.ts`.

`published` controls visibility to visitors. `curated` records that a human
has checked the details — it drives the `/admin` queue and its progress bar.

## How a change reaches the site

`getPaintings()` in `lib/paintings.ts` lists the library once (~250 ms, 258
works) and caches the result for **ten seconds** on `globalThis`. `/`,
`/gallery` and `/admin` render per request and read from that cache. Writes —
from the admin action or the webhook — clear it eagerly.

**So the guarantee is: an edit is live within ten seconds, with no restart and
no redeploy.** Not instantly. That wording is exact, and it is the third
design attempted:

1. `use cache` + `cacheTag`, invalidated by `revalidateTag`. Never worked:
   after invalidation `/gallery` kept serving old data. Tagging the page as
   well as the data, `{ expire: 0 }` instead of the `"max"` profile, and
   `revalidatePath` all failed the same end-to-end test.
2. A hand-rolled cache with eager invalidation. Passed about one run in three.
   That flakiness was the diagnosis: `next start` runs a **pool of worker
   processes**, so the webhook and the page render usually land in different
   ones. Moving the store to `globalThis` does not help — it is per-process.
   Vercel is the same, with more instances.
3. The short TTL above. Bounded, deterministic, four runs out of four at
   9–10 s.

No in-process cache can promise instant invalidation across workers. Genuinely
instant would need a shared cache such as Redis or Upstash, which is not worth
a dependency for a family gallery. If you add one, `lib/refresh.ts` is the
single place that would change.

`npm run verify:live` tests all of this against a running server. Run it after
touching `lib/paintings.ts`.

## ImageKit things that are not obvious

Each of these was found by hitting it:

- **`path` is not recursive.** Listing `path: "/paintings"` returns nothing
  when the files are in `/paintings/Netherlands`. And `filePath` is not a
  searchable field, so `searchQuery` cannot substitute. The read layer lists
  the library and filters by prefix — fine at this size, revisit in the
  thousands.
- **Folder names cannot contain spaces.** `/paintings/South Africa` is
  rejected; the folder is `South-Africa`. Display names come from
  `customMetadata.country`, never from the folder.
- **Filenames are sanitised on upload.** Anything outside `[A-Za-z0-9.\-_]`
  becomes `_`, so `WhatsApp Image (1).jpeg` lands as `WhatsApp_Image__1_.jpeg`.
  `scripts/migrate-to-imagekit.ts` mirrors that rule; without it the
  "already uploaded?" check misses and every re-run re-uploads everything.
- **`SingleSelect` rejects values outside its list**, including `""`. To leave
  one unset, omit the key entirely rather than sending an empty string — see
  `savePainting` in `app/admin/actions.ts`.
- **`files.update` replaces custom metadata wholesale.** A partial update
  blanks the fields it omits, so `bulkApply` reads each file first and merges.

## Next.js 16 notes

Built on 16.3, which moved several things:

- `unstable_cache` is replaced by the `use cache` directive; `cacheComponents:
  true` in `next.config.ts` enables it.
- `middleware.ts` is now **`proxy.ts`**, exporting `proxy` rather than
  `middleware`.
- `revalidateTag` takes two arguments; the single-argument form is deprecated.
- To force a route to render per request you need **both** `await connection()`
  and `export const instant = false`. `instant = false` alone only permits a
  blocking render — it does not stop Next prerendering a page whose data is
  cacheable.

`next/image` uses a custom loader (`lib/imagekit-loader.ts`) so ImageKit does
the resizing. That keeps the app off Vercel's image-optimization quota and
means one CDN handles every transformation.

## Auth

Two separate things, deliberately:

- **`/admin`** is behind one shared password (`ADMIN_PASSWORD`), enforced in
  `proxy.ts` before any page code runs. The cookie holds a SHA-256 digest, not
  the password. Missing `ADMIN_PASSWORD` returns 503 — it fails closed rather
  than leaving the curation screen open.
- **Visitor accounts** (Google sign-in, favourites, likes) are planned but not
  built. The family should not need a visitor account to curate, which is why
  they are not the same system.

## Not built yet

- Google sign-in with saved favourites and likes, on Supabase. Parked at the
  owner's request; needs a Supabase project and a Google OAuth client.
- PWA manifest, so the site installs to a phone home screen.
- The collection is largely untagged: at the time of writing 227 of 258 works
  have no place and 255 have no year, and most titles are machine captions
  from the old pipeline ("a painting of a waterfall"). The place and year
  filters only become useful as `/admin` gets worked through.
